## N01–N02: make delayed approval dependable

The present `driver.rs::execute_run` constructs fresh `LabRun` and `EvidenceStore` objects, then `Driver::run` waits synchronously in `review.rs::TerminalReviewer`. The live validation lost that waiting process. Neither `LabRun` nor `EvidenceStore` has a reopen API, and `RunSpec` deliberately cannot be deserialized into authority.

Use the existing clean boundary: `backend.rs::run_phase` waits for upstream shutdown; `Driver::phase` finishes the phase authority and stores evidence before returning. Seal a checkpoint after the plan is submitted and both executor/verifier projections fit the context budget. Return `prepared` as a host result while the original workflow remains `awaiting_plan_approval`; do not call it task completion.

Proposed interfaces, **not implemented yet**:

```text
codex-lab prepare <existing run options>
codex-lab run-prepared --prepared /absolute/run/evidence/prepared.json --run-id execution-001
codex-lab run <existing run options>
```

The checkpoint records validated host paths needed to resolve the original options, safe relative artifact references, task/plan bytes or hashes, workflow source and resolved selector, instruction snapshots, provider/catalog/settings fingerprints, runtime/helper hashes and the clean repository commit. The final sealed descriptor is written last. Preserve the current flat flag syntax as an alias for `run`.

`run-prepared` creates a new execution run with parent checkpoint/plan/spec hashes. It recomputes current inputs using `PreparedRuntime::load` and `RunSpec::resolve`; a changed model, role, binary, catalog, permission setting or baseline requires new preparation. Use an exclusive launch lock based on `std::fs::File::try_lock`, as used in `thread-store/src/local/writer_lock.rs`. Acquire it before revalidation and hold it through review and shutdown. It prevents competing lab hosts, not unrelated edits; recheck the baseline after review and require a quiescent task repository.

The existing `HumanReviewer` must supply a fresh decision for the new exact target before `LabRun::approve` is called. A saved checkpoint is data, not permission. Human edits create a new revision in the child run; rejection/abort/EOF cannot execute. Original planning and failed run journals remain unchanged. Metrics identify preparation and execution separately. A partial implementation is not resumable through this command.

Concrete code changes: add private `prepared.rs`, `prepared_lock.rs` and dedicated tests; extract preparation into `driver_preparation.rs`; make small calls from `driver.rs`, `cli.rs`, `lib.rs` and existing evidence/review adapters. Retain `backend.rs` shutdown, `RunAuthority` admission, and the current core dispatch seam. Add independent-process tests in `lab-runtime/tests/prepared.rs`, including the delayed decision and changed-input cases.

## N03: use a task that can expose real differences

Fixture `csv-summary-v1` has a small existing Python 3.12 API/CLI and an intentionally broken parser. The API `summarize(text: str)` aggregates category counts from an exact `category,count` header. The CLI reads one UTF-8 file and emits sorted JSON plus LF. The contract covers quoted commas, CRLF, initial BOM, empty/header-only input, blank records, repeated categories and invalid rows. Invalid headers, quoting or counts raise `ValueError`; the CLI exits 2 without partial stdout. Counts are nonnegative ASCII decimal integers; category text is preserved.

Only the project, task and public tests go into the model's committed checkout. Task, fixture tree/commit, Python version and evaluator hashes are pinned. The external evaluator runs through the existing upstream Linux sandbox after the model host shuts down, with a clean environment, no credentials/network and read-only evaluator inputs. Model-generated verification reports and independent public/hidden-test results remain separate observations.

Use `lab/fixtures/csv-summary-v1/` for the fixture and `lab/experiments/` for its setup/evaluation scripts. Tests demonstrate that the intentionally broken baseline, a no-op and a plausible incomplete fix fail, and the reference patch passes. No dependency installation, containers or benchmark framework is needed.

## Architecture critique and stop boundaries

- **Core changes and merge conflicts:** the existing phase shutdown, developer-instruction, tool-admission and provider adapters already supply the needed seams. N01–N04 require no core, TUI, sandbox, auth or session-persistence edits. If inspection disproves this, stop for a plan amendment instead of scattering hooks.
- **Approval versus session restoration:** reopening upstream threads would not restore the independent lab approval authority. A prepared data checkpoint and a fresh execution run address the observed problem with less code. General journal replay and mid-tool recovery stay out of scope.
- **Independent dimensions:** checkpoints hold canonical plans and effective settings; renderer selection comes from existing TOML. Do not revise planner/executor/verifier skills or add model branches during the representation pilot.
- **Reproducibility:** artifact hashes and current-input checks expose drift; they cannot prove immutable remote weights. Parent linkage prevents preparation and execution metrics being silently combined. Hidden tests remain isolated from the evaluated agent.
- **Configuration versus code:** keep the two existing inherited renderer profiles and direct Muse provider configuration. Add code only for the mechanically enforced checkpoint/gate, validation and comparison of recorded controls.
- **Premature abstractions:** no general backend registry, workflow event bus, evaluator plugin API, parameter sweeps, dashboard, GitHub renderer, approval daemon or automatic approval. Use small private modules and a fixed fixture first.
