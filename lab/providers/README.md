# Muse provider feasibility

The selected target is **Muse Spark 1.3 Contributor**. On 2026-09-07, Meta's authenticated developer portal and [model documentation](https://dev.meta.ai/docs/models/) confirmed the direct identifier `muse-spark-1.3-contributor` and a context window of 1,048,576 tokens. Contributor permits Meta to use submitted inputs and outputs for training and improvement. Select the tier through the exact model identifier; the API key itself is not restricted to Contributor.

Meta's dashboard Codex guide pairs that Contributor identifier with `https://api.meta.ai/v1`, `MODEL_API_KEY`, and `wire_api = "responses"`. A dedicated local credential successfully authenticated `GET /v1/models/muse-spark-1.3-contributor`; the response reported that exact ID and `owned_by = "meta"`. Its `created = 0` is not a serving revision. This read-only catalog check did not generate model output or verify inference entitlement, billing, or tool compatibility. No gateway is used in this configuration.

`muse.toml.example` pins direct Contributor routing and Meta's recommended Codex reasoning/context settings. Only the exact model-catalog path remains a placeholder. The restricted runtime refuses to start without that catalog; do not substitute the minimal model-API response for an upstream `ModelsResponse` capability catalog. This checkout no longer accepts Meta's example `model_supports_reasoning_summaries` setting: reasoning-summary support belongs in the exact catalog. A future gateway configuration must use that gateway's documented endpoint, authentication and identifier together.

The exact catalog must also satisfy the restricted host's instruction, command-tool and ambient-capability requirements described in [RUNNING.md](../RUNNING.md). Verify the provider supports those requested tool formats before populating the catalog; a model identifier alone does not supply that contract.

At the pinned Codex baseline, `ModelProviderInfo` already accepts custom `base_url`, `env_key`, and `wire_api = "responses"`; `WireApi` rejects legacy `"chat"`. No Muse-specific core branch or protocol translation has been added. The non-OpenAI provider name avoids capability selection tied to the upstream `OpenAI` name. See `codex-rs/model-provider-info/src/lib.rs` and `codex-rs/model-provider/src/provider.rs`.

The remaining compatibility checks are an actual Responses function-call/result exchange, terminal streaming events, structured plan output, accepted tool formats/request fields, reasoning replay, usage reporting, output limits, and inference access to the Contributor tier. The documented context limit is known; its behavior under pressure remains untested. Documented Responses support and authenticated catalog access do not replace an integration test. No Muse inference request has been made.

For each run, retain the requested and reported model identifiers, provider URL and adapter version if any, exact model catalog and instruction hashes, resolved context/output/reasoning settings, retries, and enabled tools. Pin `1.3` for an experiment batch; a moving `latest` alias is insufficient. Unknown fields remain explicitly unknown until verified. Codex's unknown-model metadata fallback is unsuitable as an experimental control, so the live driver requires an exact catalog entry.

Only the credential variable name/presence belongs in shareable metadata. API keys, credential-bearing headers, authentication files, and arbitrary environment dumps must not be serialized. Detailed model/tool traces may contain the submitted repository task data and remain local. Selecting the Contributor tier does not authorize collection of unrelated files.
