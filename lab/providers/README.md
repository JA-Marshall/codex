# Muse provider feasibility

The selected target is **Muse Spark 1.3 Contributor**. On 2026-09-07, Meta's authenticated developer portal and [model documentation](https://dev.meta.ai/docs/models/) confirmed the direct identifier `muse-spark-1.3-contributor` and a context window of 1,048,576 tokens. Contributor permits Meta to use submitted inputs and outputs for training and improvement. Select the tier through the exact model identifier; the API key itself is not restricted to Contributor.

Meta's dashboard Codex guide pairs that Contributor identifier with `https://api.meta.ai/v1`, `MODEL_API_KEY`, and `wire_api = "responses"`. Authenticated model metadata and subsequent live Responses probes returned the exact Contributor ID. Inference access is confirmed. The metadata's `created = 0` is not a serving revision, and these checks do not establish billing status or immutable weights. No gateway is used in this configuration.

`muse.toml.example` pins direct Contributor routing and Meta's recommended Codex reasoning/context settings. Copy [muse-contributor.models.json](muse-contributor.models.json) into the dedicated Codex home and replace the example's catalog path with its absolute path. This is the exact restricted catalog used in the live smoke run, not a provider-supplied capability document. The runtime accepted it and executed real commands. The minimal model-API response is not an upstream `ModelsResponse` catalog. This checkout no longer accepts Meta's example `model_supports_reasoning_summaries` setting: reasoning-summary support belongs in the exact catalog.

The exact catalog must also satisfy the restricted host's instruction, command-tool and ambient-capability requirements described in [RUNNING.md](../RUNNING.md). Verify the provider supports those requested tool formats before populating the catalog; a model identifier alone does not supply that contract.

At the pinned Codex baseline, `ModelProviderInfo` already accepts custom `base_url`, `env_key`, and `wire_api = "responses"`; `WireApi` rejects legacy `"chat"`. No Muse-specific core branch or protocol translation has been added. The non-OpenAI provider name avoids capability selection tied to the upstream `OpenAI` name. See `codex-rs/model-provider-info/src/lib.rs` and `codex-rs/model-provider/src/provider.rs`.

Live validation on 2026-09-07 passed Responses streaming and terminal completion, high reasoning/automatic summaries, usage reporting, encrypted reasoning replay, function calls/results, and structured canonical plan generation. Meta rejected upstream freeform `apply_patch` with HTTP 400: `custom` tools are unsupported. The catalog therefore uses `apply_patch_tool_type: null`; approved execution uses the existing function-based `exec_command`. No protocol adapter or core patch is required for this restriction.

The supplied catalog combines measured support, documented context settings, and explicit lab choices. Text-only input, disabled auxiliary capabilities, 95% context headroom, 8 KiB tool truncation and base instructions are harness settings, not measurements of all Muse capabilities. Output limits, context pressure/compaction, immutable serving revision and general task reliability remain unverified.

The first workflow smoke run **failed**, despite correct implementation and a passing Python byte check: Muse returned a displayed chunk ID in the report's API-call-ID field, which the host correctly rejected. Earlier planner attempts exposed ID-reference and approval-as-blocker mistakes. The [original validation report](MUSE_VALIDATION.md) and [observations](muse-validation-2026-09-07.json) preserve those failures.

After the lab-only planner guidance and command receipt correction, fresh research/planning produced a valid plan and its explicitly approved implementation/verification reached **completed**. The waiting planning host ended before approval was submitted; the successful replacement imported the exact reviewed plan and effective settings. This validates the restricted approved-plan execution on one tiny task, not an uninterrupted four-phase run or general reliability. See the [follow-up report](MUSE_INTERFACE_VALIDATION.md) and [machine-readable evidence](muse-interface-validation-2026-09-07.json).

For each run, retain the requested and reported model identifiers, provider URL and adapter version if any, exact model catalog and instruction hashes, resolved context/output/reasoning settings, retries, and enabled tools. Pin `1.3` for an experiment batch; a moving `latest` alias is insufficient. Unknown fields remain explicitly unknown until verified. Codex's unknown-model metadata fallback is unsuitable as an experimental control, so the live driver requires an exact catalog entry.

Only the credential variable name/presence belongs in shareable metadata. API keys, credential-bearing headers, authentication files, and arbitrary environment dumps must not be serialized. Detailed model/tool traces may contain the submitted repository task data and remain local. Selecting the Contributor tier does not authorize collection of unrelated files.
